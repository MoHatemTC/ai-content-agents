PHASE 8 BACKEND ANALYSIS
========================
ai-content-agents  (flashcards-study-revision, v0.2.0)
Analysis prepared as preparation for Phase 8: exposing the existing capability set
to Sensei AI as an API-backed backend. Read-only analysis; no code was changed.

Package layout conventions used below:
  A "document"   = one uploaded file / piece of content (Document model).
  A "chunk"      = one indexed segment of a document (Chunk model).
  A "run"        = one agent invocation (AgentRun) producing an output (GeneratedOutput).
  An "output"    = one validated artifact awaiting human review (GeneratedOutput).

================================================================================
1. ARCHITECTURE OVERVIEW
================================================================================
The product is a grounded AI content-generation platform. A user uploads
educational content (TXT/PDF/DOCX/MD), the content is parsed, cleaned,
quality-checked, chunked, and stored in both SQLite and a Chroma vector index.
Learner-facing and teacher-facing agents then generate grounded study artifacts
(flashcards, study plans, revision sessions, mentor explanations, concept
explanations, question banks, test-help) using an OpenAI-compatible LLM gateway
(LiteLLM). Every generated artifact is schema-validated, grounded against the
retrieved source chunks, and routed through a human-review gate. Nothing is
exportable (JSON/CSV/Markdown/PDF) until a human approves it.

Runtime topology today:
  - One Streamlit app (src/app.py) is the only user-facing entry point. It is a
    monolith that imports the whole library. No HTTP API exists.
  - Every layer is a plain Python package under src/; entry points are scripts
    (scripts/*.py) and python -m modules.
  - Persistence is local and process-local:
      * ingestion.db            - SQLite; documents, chunks, and the platform
                                  review/run/event tables (shared file).
      * .chroma/                - persisted Chroma vector index (ONNX embeddings).
      * src/prompts/*.yaml      - agent prompt templates (mentor, concept,
                                  question_bank, test_help).
      * src/study/prompts/*.yaml- study-agent prompt templates (flashcards,
                                  study_plan, revision).
      * .env                    - runtime configuration (LLM model, embedder,
                                  DB path, OCR toggles).

Layers (bottom to top):
  1. llm_gateway     - single OpenAI-compatible client factory. No hard LLM SDK
                       coupling outside this file.
  2. ingestion       - parse -> clean -> quality gate -> chunk -> persist.
  3. retrieval       - embed + vector index + document-scoped top-k search +
                       grounding context + reference verification.
  4. schemas/models  - shared output contracts (FlashcardSet, StudyPlan,
                       RevisionSession) and batch result models.
  5. agents          - Mentor/Concept/QuestionBank/TestHelp: raw + reviewable
                       generation, deterministic validation.
  6. study           - Flashcard/StudyPlan/Revision agents, batch generation,
                       quality benchmark, Streamlit pages.
  7. validation      - the platform layer: review lifecycle, export gate,
                       guardrails, orchestrator, end-to-end pipeline, history,
                       evaluation harness.
  8. evaluation      - offline deterministic benchmark harness for Mentor/Concept.
  9. exports         - approved-only exporters (JSON/CSV/Markdown/PDF).
  10. services       - facade isolating UI from agents (MentorConceptService).
  11. app/ui_common  - Streamlit shell + shared session-state helpers.

Two generation "families" exist with different grounding strategies:
  - agents/* (Mentor, Concept, QuestionBank, TestHelp): content-string-in,
    optional GroundedContext for reference + support verification. These feed
    the review/export platform (src/validation).
  - study/* (Flashcard, StudyPlan, Revision): deterministic topic allow-list
    extraction; outputs are always needs_human_review=True. This lane is
    self-contained; it does NOT write into the platform review store.

3. AGENT EXECUTION FLOW
================================================================================
Two families; both share the "YAML prompt -> LLM -> JSON -> Pydantic -> human
review gate" skeleton.

A) Platform agents (Mentor/Concept - src/agents):
   1. __init__: load YAML prompt; build client (injected or build_client());
      model = injected or default_model().
   2. generate(content, user_question=None, difficulty="beginner",
               context: GroundedContext|None):
        a. _build_prompt(): template.format(content=..., user_question=...,
                                             difficulty=...)  -> prompt string.
        b. _call_llm(prompt): client.chat.completions.create(model=...,
             messages=[{role:"user", content: prompt}], temperature=0.3);
             returns content.strip(); raises ValueError on empty/no choices.
        c. json.loads(raw) -> dict (JSONDecodeError -> ValueError).
        d. QuestionBankOutput/TestHelpOutput/MentorOutput/ConceptOutput
           .model_validate(dict) (ValidationError -> ValueError).
        e. verify_references(output.references, context) if context provided.
        f. validate_support(extract_claim_text(output), context) if provided;
           raises on unsupported claims / fabricated references.
   3. generate_reviewable(...) wraps the raw output via
      ValidatorBase.build_generated_output -> GeneratedOutput(status=PENDING).
   4. UI/facade only ever sees the GeneratedOutput via MentorConceptService.
   QuestionBankAgent/TestHelpAgent expose generate() only (no reviewable wrapper
   and no grounding verification yet).

B) Study agents (Flashcard/StudyPlan/Revision - src/study):
   1. FlashcardAgent.generate(content, card_format, card_count):
        a. deterministic extract_topics(content) -> allow-list of capitalized
           n-grams (no LLM).
        b. _build_prompt injects the allow-list into flashcards.yaml; prompt
           commands the model to only pick from the list.
        c. _call_llm (via src/study/llm_client.call_llm: retries, max_tokens,
           fence-stripping, JSON parse).
        d. _validate_grounding: every card.source_topic must be in allow-list,
           else GroundingError.
        e. _wrap_for_review_gate: FlashcardSet with needs_human_review=True.
   2. StudyPlanAgent.generate: same allow-list reuse (FlashcardAgent.extract_topics);
      schedules only allow-list topics; PlanGroundingError otherwise.
   3. RevisionAgent.generate: precondition - every selected_topic in allow-list
      (RevisionGroundingError before any LLM call); spaced-repetition offsets
      easy=+7d / medium=+3d / hard=+1d.
   Study outputs are rendered via src/study/formatters.py (JSON-safe dicts).

C) Orchestration (src/validation):
   - Orchestrator.run(): for each AgentSpec, call agent.generate(...), capture the
     RAW output, persist AgentRun; failures are recorded, never raised (retry with
     backoff).
   - integration.Pipeline.ingest_and_run(...): ingest -> retrieve (grounded
     context) -> run agents -> validate -> persist to PlatformStore.
   - automation.py: CLI batch runner over the whole pipeline
     (python -m src.validation.automation [--limit 1]); everything lands PENDING.

================================================================================
4. RAG PIPELINE FLOW
================================================================================
1. Ingest: ContentLoader.load_file/load_text -> parse -> clean -> quality gate
   -> chunk -> SQLiteStore (documents + chunks). Scanned-PDF OCR fallback in
   loader._recover_scanned_pdf.
2. Index: index_chunks(index, document_id, chunks) (src/study/grounding.py) or
   ChunkIndex.add_document(...) -> HashingEmbeddingFunction (ONNX) embeddings ->
   Chroma collection "content_chunks". Persisted under .chroma/.
3. Retrieve: ChromaRetriever.retrieve(query, scope=RetrievalScope(document_id))
   -> top-k (default top_k=5, min_score=0.0), score = 1 - distance, ordered
   (-score, ordinal, chunk_id); strictly document-scoped.
4. Ground: build_grounded_context(query, chunks, ...) -> GroundedContext with
   chunks, chunk_ids, is_sufficient; as_prompt_content() assembles prompt text.
   InsufficientGroundingError when not enough content.
5. Verify (post-generation): verify_references(output.references, context) and
   validate_support(claims, context) against the SAME grounded context.
6. Generate + review: agent output validated -> GeneratedOutput PENDING ->
   human approve/edit -> export.
Motivation for RAG (from src/study/grounding.py): a 1,598-page book is ~1.7M
tokens vs the 1M-context ceiling, so whole-document prompts fail with
ContextWindowExceededError; retrieval supplies scoped passages instead.

================================================================================
5. INGESTION PIPELINE
================================================================================
- Entry: ContentLoader (src/ingestion/loader.py). load_file(bytes, filename) and
  load_text(text, title, source_type). Orchestrates parser -> cleaner -> quality
  -> chunker -> store.
- Parser (src/ingestion/parser.py): TextParser.parse(data, suffix) for
  txt/pdf/docx/md (pymupdf, python-docx).
- Cleaner (src/ingestion/cleaner.py): TextCleaner.clean(text).
- Quality gate (src/ingestion/quality.py): QualityChecker.validate(cleaned);
  MIN_CHARACTERS=100, MIN_READABLE_RATIO=0.40, MIN_UNIQUE_WORD_RATIO=0.20,
  repetition-window check. Poor content is rejected.
- Chunker (src/ingestion/chunker.py): TextChunker.chunk(text, document_id);
  paragraph -> sentence -> word -> character descent; chunk_size=2000,
  overlap=200 (RetrievalConfig defaults); abbreviation window of 64 chars.
- OCR: pytesseract-based (ENABLE_OCR=true) and vision OCR via a local qwen
  model (ENABLE_VISION_OCR=true, source type "vision-ocr"). Scanned PDFs are
  recovered automatically in the loader.
- Store (src/ingestion/store.py): SQLiteStore(db_path="ingestion.db"); tables for
  documents and chunks; chunk ids are "{document_id}-c{ordinal:04d}".
- Dedup: SHA-256 of cleaned content (src/ingestion/dedupe.py).
- Batch: BatchIngestion.ingest_files/ingest_directory; per-file failure isolation.
- Demo: DemoDataLoader.load_demo_data() (5 demo documents).
- Library: document listing for the UI.

================================================================================
6. EMBEDDING GENERATION
================================================================================
- HashingEmbeddingFunction (src/retrieval/index.py): deterministic hashing-based
  embeddings (ONNX runtime, all-MiniLM-style), batch limit ~5461.
- CachingEmbeddingFunction (src/retrieval/performance.py): SHA-256 LRU cache of
  embeddings.
- RETRIEVAL_EMBEDDER=onnx in .env; Chroma client persists to .chroma/.
- Changing the embedder requires full re-ingestion (index is coupled to the
  embedder). Tests pin CHROMA_DIR and RETRIEVAL_EMBEDDER in conftest.py.

================================================================================
7. VECTOR SEARCH
================================================================================
- RetrievalConfig (src/retrieval/config.py): top_k=5, min_score=0.0,
  chunk_size=2000, chunk_overlap=200, collection name "content_chunks".
- ChromaRetriever (src/retrieval/retriever.py): protocol Retriever; scores
  top-k by 1 - cosine distance; results ordered by (-score, ordinal, chunk_id);
  honours min_score. Scope is document_id (RetrievalScope) - no cross-document
  leakage.
- Grounding assembly (src/retrieval/grounding.py): build_grounded_context ->
  GroundedContext; verifier.py (GroundingVerificationRule) checks citations.
- retrieval/benchmark.py + evaluation.py: recall@k, MRR, grounding-confidence
  benchmark over the demo corpus (run_benchmark via DemoDataLoader).

================================================================================
8. PROMPT GENERATION
================================================================================
- All prompts live in YAML under src/prompts/ and src/study/prompts/.
- Platform agents (mentor.yaml/concept.yaml/question_bank.yaml/test_help.yaml):
  template with name/description/role/instructions/output_schema/notes/
  prompt_template. Filled at runtime with .format({content}, {user_question},
  {difficulty}). Models are instructed to return ONLY schema-compliant JSON.
- Study agents (flashcards.yaml/study_plan.yaml/revision.yaml): prompt embeds the
  deterministic topic allow-list so the LLM can only reference extractable
  topics.
- Grounding/Review instructions are baked into the templates ("Use ONLY the
  uploaded educational content", "will be reviewed by a human", etc.).

================================================================================
9. RESPONSE GENERATION
================================================================================
- The LLM returns a JSON string; agents parse with json.loads and validate with
  Pydantic model_validate against the relevant Output model.
- MentorOutput: explanation, key_points, next_steps, references.
  ConceptOutput: definition, explanation, key_points, references.
  QuestionBankOutput / TestHelpOutput: typed question sets.
  FlashcardSet / StudyPlan / RevisionSession: study artifacts.
- Validated models are wrapped as GeneratedOutput (status=PENDING,
  validation_passed, validation_report) for the review pipeline, or returned
  directly (study lane) with needs_human_review=True.
- Export only after approval: assert_exportable() gates export_approved_run /
  export_output / export_outputs (src/exports/export.py) for JSON/CSV/Markdown/
  PDF (fpdf2).

12. EXISTING CAPABILITIES
================================================================================
- Full ingestion pipeline (TXT/PDF/DOCX/MD, OCR + vision-OCR fallback, quality
  gate, deterministic chunking, SHA-256 dedup, SQLite persistence).
- Persistent Chroma vector index with deterministic ONNX embeddings and
  embedding caching.
- Document-scoped top-k retrieval with provenance (chunk_ids) and a
  GroundedContext contract.
- Reference verification + deterministic claim-support validation (60% word
  overlap, negation detection).
- Six agents: Mentor, Concept, QuestionBank, TestHelp, and study lane
  (Flashcard, StudyPlan, Revision) with topic allow-list grounding that blocks
  invented topics.
- Human-review lifecycle: PENDING -> EDITED -> APPROVED (REJECT keeps PENDING),
  append-only review audit, export gate (assert_exportable).
- Batch generation with per-item failure isolation (src/models/batch.py,
  src/study/batch.py, src/validation/automation.py).
- Offline deterministic evaluation/benchmarking: groundedness, support,
  reference validity, quality, difficulty alignment (src/evaluation/*).
- Event/history logging (RUN_*, VALIDATION_FAILED, REVIEW_ACTION, EXPORT_*,
  BATCH_*).
- Approved-only export: JSON/CSV/Markdown/PDF.
- Streamlit UI wiring all of the above through review badges.
- Test doubles (tests/conftest.py) so everything is testable without an LLM.

13. MISSING CAPABILITIES (Phase 8 gaps)
================================================================================
- HTTP API layer (no FastAPI/uvicorn; backend/ is empty).
- AuthN/AuthZ, user/session identity (review "reviewer" is a free string).
- Async/background job execution - generation and ingestion are synchronous and
  serial; batch is not parallelised.
- Job queue / progress / cancellation for long-running operations.
- A real web frontend (frontend/qbank_ui.py is a placeholder; only Streamlit).
- QuestionBank/TestHelp integration: agents exist but are not wired into the
  review/export platform or the unified UI.
- Study-lane integration with the platform store: study outputs carry
  needs_human_review but are NOT written to PlatformStore/history/export gate
  (self-contained lane).
- API-key management/rotation for consumers; multi-model routing (single default
  model FW-Kimi-K2.6); no LLM fallback/retry in raw platform agents (retry only
  in src/study/llm_client.py).
- Rate limiting, request validation middleware, structured logging/observability
  for a server (history events are DB-only).
- Database migrations tooling (PlatformStore uses INSERT OR REPLACE).
- Learner-progress persistence for revision spacing (offsets are a deterministic
  heuristic, state is not stored).
- Server-side caching of expensive LLM generations.
- Cross-language search, hybrid (lexical+dense) search, multi-index management.

17. RISKS
================================================================================
- Embedder coupling: .chroma index is tied to HashingEmbeddingFunction; changing
  the embedder forces a full re-ingest (embedding is ~97% of ingest time on
  large files).
- Circular import dependency between src.validation and src.retrieval - new
  backend imports must respect the lazy PEP-562 resolution or they will break
  on partially-initialised modules.
- SQLite is single-file and shared (ingestion + platform tables); concurrent
  API traffic will need locking or a migration to a server DB. No migration
  tooling exists.
- LLM dependency: raw platform agents have no retry/fallback; a LiteLLM gateway
  outage surfaces as 60s timeouts (default timeout). Study lane has retry.
- Support validation is word-overlap-based (no semantics): "vehicle" vs "car"
  counts as unsupported -> false negatives possible with paraphrasing.
- Stale documentation: mentor-concept-lane-week3.md and parts of study docs still
  describe MOCK_MODE / OpenRouter / hardcoded mock responses, which no longer
  exist in the code (agents take injected clients; tests inject doubles). Do not
  implement from those docs.
- Dual generation stacks (src/generation legacy MockGenerator still imported by
  src/app.py vs src/agents) - understand which stack a code path uses before
  touching it.
- Context limits: RAG was designed because a 1,598-page book (~1.7M tokens)
  exceeds a 1M-context ceiling; any new "whole document" endpoint will hit the
  same wall.
- Everything generated lands in PENDING; with no human approval flow, nothing is
  ever exportable. An automated approval path must be explicit and safe.
- CI runs real embedding code (pinned CHROMA_DIR / RETRIEVAL_EMBEDDER in
  conftest.py); new tests must respect that or the suite slows/fails offline.

================================================================================
19. SENSEI FRONTEND INTEGRATION STRATEGY
================================================================================
Recommended shape for Phase 8 (two coexisting frontends during transition):
1. Stand up a FastAPI app under backend/ that imports src.* as a library (same
   pattern scripts/ already uses: insert repo root on sys.path or install the
   package - pyproject already defines it).
2. Expose resource-oriented endpoints (all returning the existing Pydantic
   models, JSON-serialisable):
     /api/v1/health
     /api/v1/documents           GET list, POST upload/ingest
     /api/v1/documents/{id}      GET metadata + chunks
     /api/v1/retrieval           POST {document_id, query} -> GroundedContext
     /api/v1/agents/mentor|concept|question-bank|test-help   POST -> GeneratedOutput(PENDING)
     /api/v1/study/flashcards|study-plan|revision            POST -> artifact + needs_human_review
     /api/v1/review              POST {output_id, action} (approve/edit/reject)
     /api/v1/exports             GET/POST approved outputs (JSON/CSV/MD/PDF)
     /api/v1/runs, /api/v1/history  audit
3. Keep the review gate server-side and authoritative: approve/edit/reject
   always go through ReviewService/PlatformStore; export always through
   assert_exportable. The API adds authentication + rate limiting around these.
4. Frontend (Sensei web app in frontend/, replacing the qbank_ui.py placeholder)
   consumes the API. Streaming/SSE optional for long LLM generations; otherwise
   synchronous with a loading state, and a job queue for ingestion.
5. Reuse tests/conftest.py doubles for offline API tests; add real endpoint
   tests in tests/test_api.py (currently a mock-client test).
6. Config via .env (LITELLM creds, PLATFORM_DB_PATH, CHROMA_DIR,
   RETRIEVAL_EMBEDDER) stays the single source of truth; a new API host/port and
   auth secret are added to .env.example.
