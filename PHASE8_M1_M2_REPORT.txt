3. M1 — AUTHENTICATION
   - No new dependencies: stdlib secrets/hashlib/hmac only.
   - Passwords: PBKDF2-HMAC-SHA256, 200k iterations, per-password salt, stored as
     "iterations$salt_hex$digest_hex"; verified with hmac.compare_digest.
   - Sessions: opaque secrets.token_urlsafe(32) access + refresh tokens. ONLY the
     SHA-256 digest of each token is persisted in the sessions table (verified in
     live run). Token TTLs from env (defaults 3600s / 86400s).
   - POST /auth/login            -> 200 {session}; wrong email OR password -> 401
                                    invalid_credentials (no account enumeration).
   - GET  /auth/me               -> 200 {user} | {user: null} when no token;
                                    invalid/expired token -> 401.
   - POST /auth/logout           -> 204; revokes the session row (revoked=1).
   - POST /auth/refresh          -> 200 {session}; rotates BOTH tokens and marks the
                                    old refresh token single-use (second use -> 401).
   - Demo accounts seeded on first startup, byte-identical to the frontend mock:
     student@demo.com / reviewer@demo.com / admin@demo.com (passwords = role).
   - Users split per DATABASE_SCHEMA.md: users (credentials) + profiles (name/
     initials) + user_roles (role, one row per (user, role), CHECK in student/
     reviewer/admin). Roles never on users.
   - Dependency wiring (backend/deps.py): get_db (per-request connection, closed
     after), get_current_user (Bearer header -> AuthUser, 401 on missing/invalid),
     require_role(*roles) -> 403 gate, ready for M3+.
   - Contract conformance: LoginRequest/LoginResponse, AuthUser, Session
     (expires_at = ms epoch), RefreshSessionRequest/Response, GetCurrentUserResponse
     all match Sensei-AI src/types/api/auth.contracts.ts. Error envelope matches
     FASTAPI_INTEGRATION.md (via backend/errors.py).

4. M2 — WORKSPACES
   - workspaces table: id PK, owner_id FK users (CASCADE), name, subject (default ""),
     description, accent, created_at, updated_at; index on owner_id.
   - GET    /workspaces            -> 200 {workspaces: [...]} scoped to caller.
   - POST   /workspaces            -> 201 {workspace}; 409 conflict on duplicate name
                                     (case-insensitive, per owner).
   - GET    /workspaces/{id}       -> 200 {workspace, data} with data = empty
                                     workspace aggregate (emptyWorkspaceData shape).
   - PATCH  /workspaces/{id}       -> 204; patch restricted to name/description/
                                     subject via PatchWorkspace schema.
   - DELETE /workspaces/{id}       -> 204.
   - Ownership: any non-owner access (GET/PATCH/DELETE) -> 403 forbidden.
   - Accent cycles primary/info/success/warning across a user's creations.
   - Contract conformance: CreateWorkspaceRequest/Response, GetWorkspacesResponse,
     GetWorkspaceResponse, UpdateWorkspaceRequest (id + patch subset), Workspace and
     WorkspaceData domain shapes match workspace.contracts.ts and types/domain.ts.
   - docs/assets/pendingReview intentionally 0 during M2: real per-workspace counts
     depend on the documents/review tables that arrive in M3+.

10. DEVIATIONS & TRADE-OFFS
   - No JWT/OAuth: opaque hashed bearer tokens chosen to avoid new dependencies
     and match the simple Supabase-like contract; refresh rotates + logout revokes.
   - M2 read model (docs/assets/pendingReview) hard-coded to 0 until M3+ adds the
     per-workspace document/review tables — the aggregate GET still returns the
     exact contract shape.
   - Workspace update validates the patch subset in the schema layer and ignores
     unknown keys (exclude_none), rather than rejecting unknown keys with 422.
   - Demo seeding runs in lifespan (dev convenience), gated on the users table
     being empty, so it never overwrites real accounts.
   - No `user_roles`-based permission enforcement beyond role membership yet;
     require_role() is wired and ready but no M1/M2 route needs it (only owner/
     self checks).
