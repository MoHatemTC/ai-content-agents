1.2 Data flow (existing, single-user CLI world)
  Document → parser → cleaner → Chunker.chunk → IngestionStore(SQLite) + Chroma
  embeddings → retrieval → Orchestrator.run_agents → GeneratedOutput per agent →
  guardrail validation (schema + grounding + reference checks) → PlatformStore
  persists run + output → OutputStatus.pending → ReviewService approve/reject/
  comment/edit → OutputStatus.approved|rejected (terminal) → assert_exportable
  gate → export (JSON/CSV/Markdown/PDF). SystemEvent rows log everything.

1.3 Storage
  ingestion.db : documents(id,title,content,source_type,file_type,created_at,
                content_hash) + chunks(id,document_id,text,ordinal,start_char,
                end_char) + platform tables (events, metrics).
  platform.db  : agent_runs(id,agent_name,input_context,source_chunk_ids,
                prompt_ref,model,started_at,finished_at,status,error) +
                generated_outputs(...) + reviews(append-only) + system_events.
  .chroma/     : deterministic ONNX HashingEmbeddingFunction vector store.

1.4 Dependency / invocation graph (what a FastAPI layer can call TODAY)
  HTTP layer → src/agents, src/study, src/ingestion, src/retrieval,
  src/validation (orchestrator/review_service/history/store), src/llm_gateway.
  Everything is constructible without a network service: agents take
  `client: Any | None`; tests/conftest.py proves the seams are injectable.
  `src/validation.integration.Pipeline.ingest_and_run` already chains
  ingestion → indexing → orchestration in one call.

1.5 The contract reality gap (frontend → backend)
  The frontend was built for a multi-user Supabase-backed FastAPI (auth, roles,
  workspaces, per-doc status/pages/size/notes/tags, generation versions, chat
  history, review queue/audit, notifications, analytics, search, model/agent
  catalogues). The existing backend is a single-user, workspace-free CLI study
  platform. None of the Supabase concepts exist in backend code. Every frontend
  endpoint therefore needs (a) an HTTP router that does not exist and (b) an
  adapter that translates contract JSON ↔ backend Pydantic/DB models. Sections 2
  and 3 enumerate exactly which of those are "reuse existing", "wrap existing",
  and "must be built new".

4. RISKS
================================================================================

4.1 Circular import src.validation ↔ src.retrieval. Validation's
  grounding_rule/guardrails import retrieval types; integration imports
  ingestion + retrieval. Any new facade that imports validation AND retrieval
  directly can recreate the cycle — keep the existing lazy-import pattern
  (src/validation/__init__.py __getattr__). Constraint: do not reorder imports
  blindly.

4.2 Duplicated logic. Library.delete_document vs Store.delete_document are two
  code paths; ingestion.db vs platform.db are two databases; there is no single
  document lifecycle. The upload/delete adapter must decide which store owns
  "the document" and keep Chroma in sync or the two diverge silently.

4.3 Review-gate is terminal. OutputStatus.rejected is terminal — the contract
  has no "reuse/re-generate" endpoint, so a rejected question cannot return to
  the queue without a new generationId. The frontend's Needs Edit ↔ edited
  mapping must not accidentally allow reject→pending transitions
  (is_legal_transition review_schema.py:94).

4.4 Retrieval/embedding semantics. Chroma uses a deterministic hashing embedder
  (no semantic similarity). Search + RAG retrieval results are therefore exact/
  hash-overlap based; contract "grounding_score" and search relevance may read
  weaker than a real LLM-embedding product. Do not misrepresent these scores as
  semantic.

4.5 Auth is not a bolt-on. Roles gate review/approve and owner/admin gates on
  PATCH/DELETE (BACKEND_CONTRACT.md). Shipping workspaces/documents/review
  before auth leaves every endpoint open; the auth milestone must land first or
  everything else is built against a phantom.

4.6 Frontend/client contract looseness. Client accepts bare JSON or
  {data:…}; pagination and exact field presence vary across contract files
  (e.g. GET /chats returns nested messages, GET /workspaces returns flat list).
  Adapters must target the exact contract types, not "close enough" shapes.

4.7 Single-file SQLite concurrency + long generations. One platform.db writer
  + blocking LLM calls (90s client timeout) means upload/generate handlers need
  background task handling (202/timeout semantics) or the client times out
  while a run is in flight. No worker/queue exists today.

4.8 Study lane wiring. Study agents' review-gate lives inside each agent's
  _wrap_for_review_gate; the question/test-help agents do not wrap at all.
  Orchestrator run_agents bypasses those private wrappers for some lanes — the
  facade must reuse the exact path that sets OutputStatus.pending or review
  queue stays empty.

5. RECOMMENDED IMPLEMENTATION ORDER (milestones)
================================================================================
Each milestone is independently shippable and testable against the frontend's
mock-free mode. Frontend flip (isMockMode=false) is the acceptance check.

  M0  Scaffold: FastAPI app, config, error envelope, CORS, migration runner,
      DI skeleton, /health. Zero domain changes.
  M1  Auth: users/profiles/roles, login/logout/me/refresh, bearer DI, role
      guard. Unlocks everything (4.5).
  M2  Workspaces: tables, CRUD, slug conflict (409), membership, workspace
      aggregate GET (docs/questions/flashcards/chats/history/weakTopics/audit).
  M3  Documents/upload: upload/parse/chunk/embed/list/chunks/delete + notes,
      reusing Loader/Chunker/index_document; workspace + metadata columns;
      Chroma/SQLite sync (4.2).
  M4  Retrieval: ensure Chroma index is built per workspace; grounding +
      citation serialization into generation payloads (reuse ContentReference).
  M5  Generation: wrap QuestionBank/TestHelp into the review-gate path like the
      study lane (4.8); generationId/kind/scores envelope; per-item review/
      estMinutes/citations.
  M6  Chat: chats/chat_messages tables; POST/GET /chats; mentor/concept message
      handlers around existing agents + citations.
  M7  Review: approve/reject/needs-edit/comment via ReviewService, + flag and
      queue/audit read models, reviewer identity from auth, workspace filters.
  M8  Exports: assert_exportable + existing exporters behind an export facade
      (not in the contract's endpoint list but required by review-gate flow).
  M9  History/analytics: history rows from AgentRun/Output/Review; analytics
      facade over persisted bloom/type/quality/topic data; search facade
      (documents/questions/flashcards kinds).
  M10 Catalogue/models/notifications: agents metadata, pipeline steps/stages,
      notifications CRUD, /catalogue demo, /models registry.
  M11 Frontend flip + contract conformance pass per BACKEND_CONTRACT.md rule 4
      (paths → contracts → api → service order), then full integration tests.

Cross-cutting: tests at every milestone using tests/conftest.py LLM doubles;
keep the lazy-import constraint (4.1); never reorder src/validation exports.
