3. CODE CHANGES — what each file does & why
   - src/retrieval/models.py: RetrievalScope gained an optional workspace_id.
     At least one of document_id/session_id/workspace_id must be set; a
     workspace-only scope maps to no Chroma metadata filter (to_where() now
     returns dict | None). WHY: /search targets a whole workspace, and since
     one workspace IS one collection, workspace-wide retrieval = query with
     no filter — which the old scope structurally forbade. Extending the
     domain model (Option A, approved) keeps retrieval logic in src/retrieval
     instead of duplicating Chroma query semantics in backend/. Fully
     backward-compatible: all existing call sites pass document_id.
   - backend/search/schemas.py: contract-faithful shapes — SearchQuery-driven
     response {results, total}, SearchResult {id, kind, title, subtitle?, to}.
     kind accepts the full SearchResultKind union but only "document" is
     produced in M4 (question/flashcard/concept/history depend on M5/M6/M10).
   - backend/search/service.py: opens the workspace index via ChunkIndex
     (same workspace_<id> collection scheme and RetrievalConfig persistence
     as the M3 embed path), retrieves with ChromaRetriever (min_score floor,
     deterministic ranking), groups chunks per document (best score wins),
     hydrates title/kind/pages from the persisted documents table, and maps
     to SearchResult with the mock-shaped subtitle "{kind} · {pages} pages"
     (kind alone when pages is null). Also exposes build_grounded_context ->
     GroundedContext for M5 (as_prompt_content / to_content_references /
     chunk_ids).
   - backend/search/router.py: GET /search?q=&workspace_id=&limit=&kinds=
     with the contract's error envelope: 401 no token, 403 non-owner, 404
     unknown workspace, 422 missing q / workspace_id / bad limit (FastAPI
     validation is already enveloped by backend/errors.py). limit clamped to
     1..100, default 40 (the frontend mock's default).
   - backend/main.py: registers search_router (one line each for import and
     include).

4. ARCHITECTURE DECISIONS
   a) Workspace-wide scope = domain extension, not backend bypass (Option A,
      explicitly approved). RetrievalScope.workspace_id is the one place that
      knows a workspace collection needs no filter. The same scope will serve
      M6 workspace chat and M5 grounded generation unchanged.
   b) Search reuses the M3 collection scheme (workspace_<id>, Chroma dir from
      Settings.chroma_dir) and the M3 write path keeps index rows in sync, so
      M4 adds NO new write path — only read-only retrieval.
   c) One result per document: retrieved chunks are grouped by document_id
      with the best chunk score; titles come from the DB (persisted metadata,
      decision 3), never from index text.
   d) kinds filter is truthful: only "document" exists in M4; a kinds filter
      excluding documents short-circuits to empty rather than pretending other
      kinds exist.
   e) Embedder semantics are exposed honestly (decision 5/analysis 4.4):
      ranking is whatever ChromaRetriever returns for the current embedder
      (hashing = exact keyword overlap, deterministic; onnx = semantic).
      Blank queries short-circuit to empty (retriever behaviour reused).
   f) Grounding plumbing is a thin adapter over GroundedContext — M5 consumes
      the same object (as_prompt_content / to_content_references /
      chunk_ids), so grounding scores, citations (ContentReference) and
      source_chunk_ids need no new retrieval code in M5.

14. DEVIATIONS & TRADE-OFFS
    - M4 serves document-kind results only; question/flashcard/concept/history
      kinds return empty (their data arrives in M5/M6/M10).
    - Search matches content, not titles, because Chroma indexes chunk text;
      a title-only match for an unparsed/never-embedded document cannot appear.
      Accepted for M4 (title metadata is searchable once embedded); a LIKE
      fallback over documents.title is a possible M9 enhancement.
    - One Chroma open per request (matches the M3 embed/delete pattern);
      acceptable at this scale, revisit if search latency matters.
    - hashing embedder in offline/test mode does exact-token matching; results
      honestly reflect the embedder (decision 5). Prod default is onnx.

15. REMAINING WORK / RISKS / BLOCKERS
